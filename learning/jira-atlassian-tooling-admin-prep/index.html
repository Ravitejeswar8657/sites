1. What the role really is

It's a developer-tools platform admin and support role, not hands-on infrastructure DevOps. You own the tools R&D engineers use every day: keep them running, configure them, handle tickets within SLAs, test upgrades and migrations, and improve how engineers work.

Roles like this often rate candidates higher if they can script (Python/JS) and understand how the applications are built. Frame automation work as "productivity and developer-experience improvements."

3. Confluence

Atlassian's team wiki. Jira tracks the work; Confluence holds the knowledge about the work.

Structure

Site → Spaces (one per team/product, own permissions) → Pages (a tree with parent/child pages and version history) + blog posts.

Permissions: three layers

  1. Global: who can use Confluence and create spaces.
  2. Space: view, add, edit, delete, administer. Grant to groups.
  3. Page restrictions: lock one page for view/edit. A restriction on a parent applies to its children.
"A user can't see a page": licence → group with space access → restriction on the page or any parent page.

Features to know

  • Templates and blueprints for meeting notes, decision logs, retros, how-tos.
  • Macros: Jira Issues (live JQL list), Page Tree, Excerpt/Include, status labels, code blocks, panels.
  • Labels and search to keep knowledge findable; Jira integration (link issues, create issues from text, requirement pages on epics).

What an admin does

Creates spaces and permissions for new teams, manages LDAP/SSO-synced groups, maintains templates, archives stale spaces, manages Marketplace apps (e.g. draw.io), plans upgrades or Cloud migrations on staging first, answers how-to tickets.

Likely questions

  • Set up a space for a new R&D team.
  • Keep docs from going stale: owners, review dates, archiving, templates.
  • Move docs between spaces: move/copy, export/import, fix broken links.
  • Confluence is slow: attachment size, heavy macros, logs, database, JVM memory (Data Center).

4. Company-managed vs team-managed projects

Think of an apartment building. Company-managed is a building where management sets the rules for every flat: change the lock design once and every flat gets it. Team-managed is an independent house: the owner decides everything, quickly, but nothing is shared. (Newer Jira screens may call projects "spaces.")

Company-managedTeam-managed
Configured byJira adminsThe team's project admin
Workflows, fields, screensShared schemes reused by many projectsInside one project, not shared
Changing one thingAffects every project using that schemeAffects only that project
PermissionsPermission schemes with roles and groupsSimple access level + Admin / Member / Viewer
Best forLarge organizations needing standardsSmall, independent teams

Example: 50 R&D projects must share one Bug process. Company-managed: build one workflow scheme, attach it to all 50, edit once. Team-managed: 50 slightly different workflows, edited 50 times.

"Company-managed projects are configured centrally by admins using shared schemes, so one configuration gives consistency across many projects. Team-managed projects are configured by the team itself and aren't shared. For many R&D teams, company-managed is the right choice, and it's where most admin work happens."

Converting? No direct switch: create a project of the other type and move the issues, then check field and status mapping.

5. Jira permissions

Four layers, like airport checkpoints. A user must pass every one.

  1. Product access: do they have a Jira licence? (admin.atlassian.com)
  2. Global permissions: site-wide powers: Administer Jira, browse users and groups, share dashboards/filters, bulk change, create team-managed projects. Give sparingly.
  3. Project permissions (permission scheme): what they can do inside a project. Most tickets come from here.
  4. Issue security: optional lock on individual issues (e.g. security bugs).

Key project permissions

PermissionAllows
Browse ProjectsSee the project and its issues. Without it, the project is invisible.
Create / Edit IssuesCreate new issues / edit fields
Transition IssuesMove issues through the workflow
Assign Issues / Assignable UserAssign to others / be assigned
Resolve / Close IssuesSet resolution, close
Delete IssuesDelete (usually admins only)
Administer ProjectsManage roles, components, versions
Manage SprintsStart and complete sprints

Grant to: project role (best), group, user (avoid), or special entries like Reporter, Current Assignee, Any logged-in user, Public (avoid).

Groups vs project roles

Groups are site-wide and usually synced from AD/SSO. Roles are per project. A scheme says "Developers can edit issues"; each project fills its own Developers role. So one scheme serves hundreds of projects.

Best practice: scheme → grant to roles → projects add groups to roles → groups come from AD/SSO, so offboarding removes access automatically.

Troubleshooting flow

  1. Product access (licence).
  2. Permission Helper (admin): enter user, project, permission; it explains exactly why.
  3. Role and group membership.
  4. Issue security level on that issue.
  5. Can't move an issue? Check the workflow condition on that transition, not just permissions.

Best practices

  • Copy the default scheme before editing; use few, standard schemes.
  • Least privilege for Delete Issues and Administer Jira.
  • Audit via the audit log; remove inactive users to free licences.

Related settings: notification scheme (who gets emailed on which events), issue security scheme, field configuration (required/hidden fields — often confused with permissions).

6. Hands-on Jira Cloud lab (about 4–5 hours)

Newer Jira Cloud screens call issues "work items."

Step 0 — Set up

Sign up for free Jira Cloud and invite a second user (another email) to test permissions. If admin features are greyed out on Free, start the Standard trial.

Step 1 — Project

Create a Scrum, company-managed project, e.g. "R&D Tools", key RDT.

Step 2 — Use it as a user

Create an Epic, three Stories, two Bugs, a Sub-task. Create and start a sprint. Move cards across the board. Add Components (Firmware, Mobile App) and a Version (v1.0).

Step 3 — Custom fields and screens

Create a select-list field "Affected Environment" (Dev, QA, Prod), add it to the project's screens, confirm it shows on a Bug.

Screen → Screen scheme (create/edit/view) → Issue type screen scheme (per issue type) → project. Also check the field's context.

Step 4 — Custom workflow: only QA can close bugs

  1. Copy the workflow as "RDT Bug Workflow": Open → In Progress → In Review → QA Testing → Closed, plus Reopen.
  2. On Close add a condition (User is in group qa-team), a validator (Resolution required) and a post function (set resolution).
  3. Map Bug to it in a workflow scheme, attach to RDT, map old statuses.
  4. Test with a user outside and then inside qa-team.
Conditions hide, validators block, post functions act.

Step 5 — Permissions and roles

Copy the default permission scheme, grant to roles, attach to RDT. Remove Browse Projects from your second user's role, confirm the project disappears, check the Permission Helper, restore.

Step 6 — JQL, filters, dashboards

project = RDT AND issuetype = Bug AND status != Closed
assignee = currentUser() AND sprint in openSprints()
created >= -7d AND priority in (High, Highest)
project = RDT AND updated <= -30d AND statusCategory != Done

Save one as a filter; build a dashboard with Filter results and a pie chart.

Step 7 — Automation

  • Highest-priority Bug created → assign and comment.
  • All sub-tasks done → transition parent to Done.
  • Weekly: issues not updated in 30 days → comment pinging the assignee.

Use each rule's audit log to debug rules that didn't fire.

Step 8 — Python against the REST API

import requests
from requests.auth import HTTPBasicAuth

SITE = "https://your-site.atlassian.net"
auth = HTTPBasicAuth("you@example.com", "YOUR_API_TOKEN")

r = requests.get(
    f"{SITE}/rest/api/3/search/jql",
    params={"jql": "project = RDT AND issuetype = Bug AND statusCategory != Done",
            "fields": "summary,status,assignee"},
    auth=auth,
)
r.raise_for_status()
for issue in r.json()["issues"]:
    f = issue["fields"]
    who = f["assignee"]["displayName"] if f["assignee"] else "Unassigned"
    print(issue["key"], "|", f["status"]["name"], "|", who, "|", f["summary"])

Create the token at id.atlassian.com → Security → API tokens. Check Atlassian's REST docs if an endpoint has changed.

7. Jira Q&A — 20 answers to say out loud

1. What is Jira?

Atlassian's work-tracking tool. Teams plan, track and release work through projects, issues (work items), workflows and boards, usually with Scrum or Kanban, integrated with Confluence, Bitbucket and CI tools.

2. Team-managed vs company-managed?

Team-managed: configured by the team, simple, nothing shared. Company-managed: controlled by admins through shared schemes, so one configuration serves many projects consistently.

3. What is a scheme? Name the main ones.

A reusable configuration attached to projects: workflow, permission, notification, issue type, issue type screen, field configuration, issue security.

4. What is a workflow?

The statuses an issue moves through and the transitions between them. Transitions can carry conditions, validators and post functions.

5. Conditions vs validators vs post functions?

A condition controls whether a user sees the transition. A validator checks input before it completes. A post function runs after it. Conditions hide, validators block, post functions act.

6. How do you make sure only QA can close bugs?

Copy the Bug workflow, add "User is in group qa-team" on Close, map Bug to it in the workflow scheme, publish, test with users inside and outside the group.

7. A user can't see a project — troubleshoot.

Licence → Browse Projects in the permission scheme → are they in that role/group → issue security if it's specific issues. Use the Permission Helper.

8. A field doesn't appear on the Create screen — why?

Trace screen → screen scheme (Create) → issue type screen scheme for this issue type → field context → field configuration (hidden?).

9. Groups vs project roles?

Groups are site-wide (often AD/SSO). Roles are per project. Grant permissions to roles, put groups in roles, so one scheme serves hundreds of projects.

10. Add a new status without breaking existing issues?

Edit a draft/copy, add the status and transitions, publish; Jira asks you to map existing issues from removed statuses. Test on a test project first and tell users.

11. JQL: open high-priority bugs from the last 7 days 
project = RDT AND issuetype = Bug AND priority in (High, Highest)
AND statusCategory != Done AND created >= -7d

statusCategory works across different workflows.

12. Example automation rule?

Highest-priority Bug created → assign to on-call lead and comment. Or: all sub-tasks done → parent to Done. Debug with the rule's audit log.

13. Epic vs story vs task vs sub-task vs bug?

Epic: large body of work across sprints. Story: user-facing requirement. Task: technical work. Bug: defect. Sub-task: breakdown of any of these.

14. Scrum board vs Kanban board?

Scrum: time-boxed sprints, backlog, planning, velocity. Kanban: continuous flow with WIP limits, suits support and ops.

15. Components vs versions vs labels?

Components: sub-parts of a project, can have default assignees. Versions: releases. Labels: free-text tags, messy at scale.

16. Bulk-update 200 issues?

Simple: bulk edit from search results. Complex or repeatable: Python against the REST API with an API token; test on a few issues and log changes.

17. Jira Cloud vs Data Center?

Cloud: hosted by Atlassian, automatic upgrades. Data Center: self-hosted, more control, clustering, more admin work. Server licences ended Feb 2024.

18. Plan a Data Center upgrade?

Release notes and app compatibility → back up DB and home directory → upgrade staging and run UAT → announce a maintenance window → upgrade prod → validate, with rollback ready → document.

19. Jira is slow — where do you start?

Scope it (everyone or one board/filter), heavy JQL in filters and dashboards, large boards, misbehaving automation or apps; on Data Center, logs, JVM memory, database.

20. Request to add a custom field?

Check whether an existing field covers it (too many fields slow Jira). If needed, create it with the narrowest context and add it only to relevant screens.

Practise 5, 7 and 8 out loud — they come up most.

8. Other question bank

Bitbucket, Jenkins, Bamboo, Artifactory

  • Protect main: branch permissions + merge checks (required approvals, passing build).
  • Gitflow vs trunk-based development.
  • Declarative vs scripted Jenkins pipelines; agents; shared libraries.
  • Build fails on one agent only: tool versions, disk space, credentials, network, workspace.
  • Safe Jenkins/plugin upgrade: backup, staging, compatibility check, rollback plan.
  • Bamboo vs Jenkins: Bamboo integrates natively with Jira/Bitbucket; Jenkins is open source and plugin-heavy.
  • Artifactory local / remote / virtual repos; control storage with retention and cleanup policies.
  • GitHub Actions → Jenkins mapping: workflow file ≈ Jenkinsfile, runners ≈ agents, secrets ≈ credentials.

Platform and support

  • Cloud vs Data Center migration; evaluating a Marketplace app; users at scale via SSO/AD groups.
  • Incident vs service request vs problem vs change; SLAs; prioritise by impact × urgency.
  • Tool down for 500 engineers, first 30 minutes: acknowledge, communicate, triage, escalate, restore, then root cause.
  • Documenting changes: change record, runbook, knowledge article.

Behavioural (prepare STAR stories)

An incident under pressure · automating a repetitive task · a difficult stakeholder · learning a new tool quickly · a deployment that went wrong.

Questions to ask them

Cloud or Data Center, any migration planned? How big is the user base and the tooling team? Mostly tickets or improvement projects?

9. CI/CD project story — checklist

A strong story covers three layers, then rollback and results:

  1. PR gate: branch protection, required review approval, merge only when checks pass.
  2. CI on every PR: build, unit tests (developers write them, the pipeline enforces them), code-quality scan with a quality gate, image build. Results show on the PR.
  3. CD after merge: immutable image tag (version + commit SHA), push to registry, promote the same artifact Dev → QA → Prod with a manual approval before prod. Never rebuild for prod.
  4. Rollback: redeploy the previous tag; on Kubernetes, kubectl rollout undo; on Azure App Service, deployment-slot swap.
  5. Results: before/after numbers, even rough ones.

Gaps interviewers probe

  • Exactly how you deploy to Kubernetes (manifests, Helm, set image) and whether you used readiness probes.
  • How the pipeline authenticates to the cloud: OIDC federated credentials > service principal secret > hard-coded (red flag). How the cluster pulls from the registry.
  • Security scanning (Trivy, Defender, Dependabot) — or say it was the next step.
  • Database changes must be backward-compatible so rollback stays safe.
  • Speeding up a slow pipeline: dependency and layer caching, parallel jobs, running only affected tests.
Only name tools you actually used. Every name you say is a follow-up question.
